# 신호 검출기 실차 비교 기록 — 2026-10-11

사용자가 시동을 켠 차량에 새 검출 방식의 비교 시험을 반영하고, 푸시한 내용과 같은 코드인지 확인하도록 요청했다.
직전 `8f6e643122`의 주간 검출기는 분석 호출에서만 선택할 수 있었으므로, 이번에 실시간 기록 연결을 추가했다.
이 작업은 알려진 녹색 해제 실패를 고쳤거나 새 검출기의 차량 제어 적용을 승인한 것이 아니다.

## 비교 모드

기존 관측 opt-in `enabled=1`, `tracking_enabled=1`에 더해, 해당 차량의
`/data/signal-color-shadow/daytime_comparison_enabled=1`을 시작 시 읽는다.
없는 차량은 기존 경로 그대로다. 공개 설정이나 공용 기본값은 추가하지 않았다.

하나의 signalcolord에서 카메라 영상을 한 번 복사한 뒤 기존 검출기와 새 주간 검출기를 순서대로 실행한다.
두 검출기는 같은 프레임 ID·카메라 시각·RGB를 사용하지만 객체 추적 상태는 독립적이다.
카메라 재연결·시각 이상·복사 실패 시 둘 다 초기화한다. 모드 파일이 바뀌면 현재 실행을 끝내고 다시 시작한다.

- 기존 결과: `signalTrackingShadow`, `tracking_latest.json`.
- 새 결과: `signalTrackingDaytimeShadow`, `daytime_comparison_latest.json`.
- 두 기록 모두 알고리즘 해시, session, 프레임 ID, 입력/결과 나이, 처리 시간, 추적 대상과 판정을 포함한다.
- 새 결과의 `pair_work_ms`는 복사부터 두 검출기가 끝날 때까지의 시간을 포함한다.
- 두 방식 모두 `control_permission=False`, `assist_transport=False`다. **비교 모드에서는 제어용
  `/dev/shm/carrot_signal_observation.json`에 어느 결과도 게시하지 않는다.** 별도로 assist를 켜도 새 결과가
  제어 입력으로 전달되지 않는다. 설치 시 기존 `assist_enabled`도 0으로 둔다.

최대 20Hz, 코어 0–3/nice19, 합산 CPU duty 목표 50%를 유지한다. 순차 비교이므로 두 번째 결과의
카메라 기준 나이는 첫 계산 시간을 포함한다. 이 수치를 단독 실행 속도의 공정한 A/B 비교로 해석하면 안 된다.
추가 계산에 따른 실제 관측 간격과 250ms 추적 만료 발생은 로그에서 확인해야 한다.
원래 주행 ONNX, x·v, 정상 종방향·횡방향 제어, 신호 해제 조건은 이번 연결 작업에서 변경하지 않았다.

## 확인 및 설치 절차

관련 데스크톱 테스트 **329개 통과**. 비교 opt-in, 독립 추적 상태와 재생성, 적색/녹색/unknown 모두
제어 전달 차단, 실제 worker의 한 프레임 처리에서 두 로그·최신 파일 생성 및 제어 게시 0회를 확인했다.
기존 신호 관측·보조·플래너·관련 현대 제어 회귀 테스트도 함께 실행했다.

차량은 기존 `carrot-signal-shadow`의 `b80db2c97d`였다. 설치 전 최신 Park·정지·제어 비활성을 확인하고,
추적 파일 변경이 없는지 검사한 뒤 저장소 lock 아래 원격 `carrot-wip`의 지정 커밋으로 전환한다.
untracked 빌드 파일은 삭제하지 않으며 충돌이 있으면 중단한다. 정상 DoReboot 경로를 사용하고,
부팅 후 커밋·코드 해시·원래 ONNX 해시·비교 로그·모델/플래너 상태를 확인한다.

차량별 opt-in 파일은 Git 밖에 있으므로 **동일 커밋을 받는 다른 차량에서 시험이 자동으로 켜지지는 않는다.**
비교 모드를 끄려면 해당 파일을 0으로 바꾼다. assist OFF는 그대로 유지되며 자동으로 다시 켜지지 않는다.
이전 주간 검출 실패와 속도 시험은 [수정 시도 기록](signal_day_latency_fix_20261011.md)을 참조한다.
설치 결과와 원시 자료는 `.analysis/archive/2026-10-11-signal-live-comparison/`에 비공개로 보관한다.

## 설치 완료와 P단 실행 확인

원격에 푸시한 `aa010a940e`를 차량 `carrot-wip`에 설치하고 정상 DoReboot 경로로 재부팅했다.
차량의 tracker와 worker 파일 SHA-256이 해당 Git blob과 정확히 일치했다.
원래 `driving_supercombo.onnx` SHA-256은
`f73a9e535523d5e9acb9e642c64e33d631825dc8ba74123757d107cedd047bb5`로 유지됐다.
차량별 비교 모드는 ON, 기존 신호 도우미의 `assist_enabled`는 OFF다.

새 부팅 이후 P단 25초 측정에서:

- 모델 499프레임, 약 19.96Hz, 모두 유효하고 연속 ID. 모델 계산 평균 24.97ms.
- 플래너 499개 모두 유효. CAN 유효, 주요 프로세스 PID 유지.
- 기존/신규 관측 각각 181개, 같은 카메라 frame ID 181쌍. 두 관측 모두 181/181개 fresh.
- 카메라 기준 결과 나이 p95: 기존 123.17ms, 신규 151.38ms. 신규는 앞선 기존 계산 시간도 포함한다.
- 관측 프레임 간격 p50/p95 모두 3프레임, 약 150ms.
- 두 로그 모두 비교 모드 및 제어 전달 OFF. 제어용 관측 파일이 갱신되지 않음을 확인했다.

첫 설치 시 Git fetch 동안 수신하지 못한 상태를 한 번만 갱신해 신선도 검사가 실패했으며,
코드 전환 전에 멈추고 도우미·관측기를 OFF로 두었다. 신선한 상태를 제한 시간 안에 다시 모으도록
설치 도구만 수정한 뒤 같은 Park·정지·비활성 검사를 통과해 설치했다. 검사를 완화하지 않았다.

이는 설치·기록·처리 부하 확인이다. 실제 신호 앞에서의 검출 정확도와 추적 지속성은 후속 주행 기록으로
평가하며, 비교 결과로 차량이 감속하거나 출발하도록 연결하지 않았다.
