# S3 H.264 transport and firmware 1.2.0 — 2026-10-16

## Change

Updated C4 code selects H.264 after an authenticated capability response from
S3 firmware 1.2.0. C4 encodes and the TURZX 1cbe:0092 panel decodes; S3 forwards
the existing USB video protocol. This is not an ESP32 video decoder.

The Wi-Fi default is 1 Mbps, GOP 10, bounded 64 KiB chunks, and the existing
15 FPS target / 10 FPS eGPU cap. Hardware/software encoder selection remains
available. Auto encoder initialization fallback can still reach JPEG. Older S3
firmware and missing capability replies use JPEG; a registration can explicitly
choose `auto`, `jpeg`, or `h264`. Explicit H.264 requires verified support.

Preserve reference-frame order: never retain only the newest P-frame after
dropping its references. A full three-access-unit queue times out after 250 ms
and requests a clean session restart. The sender exits even if shutdown cannot
enqueue a sentinel. Direct USB pacing and its prior queue policy remain separate.

Firmware treats successful command 121 video chunks as display activity for
wake, idle shutdown and LED feedback. Host shutdown stops video, then uses sync
and brightness zero. Existing NVS, pairing, phone setup, UART provisioning and
JPEG behavior remain compatible. No OTA or private flash image is distributed.

## Comparisons and physical tests

Private artifacts are under `.analysis/scratch/2026-10-15-egpu-s3/`; they contain
device identifiers/registration material and are not public release inputs.

- Earlier C4 JPEG stress: detailed Q40 112,002 bytes/frame reached 3.54 FPS;
  Q20 72,461 bytes reached 6.93 FPS. Noise Q90 799,271 bytes reached 0.50 FPS.
  These use precompressed frames, so the measured bottleneck was not rendering.
- Offline moving 40-frame comparisons, padded 464×1920, H.264 1 Mbps:
  73.58% fewer bytes for a simple HUD and 75.73% for detailed content versus
  JPEG Q40. Both decoded 40/40. This is not equal-quality benchmarking, and PC
  software encoding time does not establish native C4 performance.
- Physical simple H.264: 601 frames / 60.0595 s, 601 acknowledged chunks;
  USB mean 11.46 ms, maximum 124.04 ms. User confirmed smooth motion and correct
  orientation.
- Final 1.2.0 app, detailed H.264: 589 frames / 60.1143 s (9.80 FPS), 633
  acknowledged chunks; USB mean 12.19 ms, maximum 63.86 ms. Pairing preserved.
  More chunks than frames reflect large access-unit splitting.
- Native C4 hardware encoder starts at 464×1920, 1 Mbps, GOP 10. User confirmed
  the actual vehicle HUD's direction, colors and numbers. Recorded steady
  windows are about 0.9–1.0 Mbps with queue maximum one, zero dropped units,
  and mean send calls about 1–3 ms. Host refresh often reaches 9–10 Hz but has
  lower intervals; this is not a guaranteed 10 optical FPS result.

AP association changed between channel 6 / about -50 dBm and channel 1 /
about -70 dBm across flashes. The detailed final test used the weaker link.
Do not attribute every before/after difference to the codec or claim the radio
root cause fixed. Synthetic ACK throughput is not an optical panel measurement.

## Native lifecycle and model checks

Selective installation changed only five HUD runtime files on the parked C4,
with backups, matching source hashes and fresh Park/zero/inactive/panda checks.
It did not update or restart the model, controls, manager or eGPU worker.

Initial native 60 s: model and DM each published 1,200 valid consecutive frames,
20.0074 / 20.0084 Hz, zero missing IDs; eGPU and S3 remained active. This bounded
check does not promise fault-time 20 Hz.

A separate 300 s memory watch kept the same HUD PID connected in every 30 s
sample: PSS 184.95 to 185.66 MiB, 104 FDs throughout, available memory 553.5 to
555.6 MiB. It is a bounded observation, not a long-duration leak clearance.
Its synchronous `/proc/PID/smaps` reads made the conflating frame observer miss
one model and DM message at each of the nine 30 s boundaries. That combined
probe's 19.973 Hz / nine missing IDs must not be presented as a clean model
pass or attributed to production frame loss without independent evidence.

The final independent 300.007 s frame-only capture, with the final host files,
records 6,000 valid consecutive model frames at 20.00092 Hz and no missing IDs.
DM records 6,000 valid updates at 19.99806 Hz with one frame-ID gap and a maximum
96.14 ms arrival interval; do not describe this as a strict 20 Hz DM pass.
The original model/DM/eGPU processes remain running and S3 is connected at the end.

Two managed H.264 HUD stops each reclaimed all six allocations owned by that
HUD PID. Available memory recovered from 551.2 to 650.7 MiB and from 553.2 to
644.5 MiB. Existing unrelated historical allocations were unchanged. Reopening
and closing a bounded number of sessions is not proof of a long memory plateau.

A deliberate disconnect of only the S3 TCP connection recovered in 20.205 s,
with the same HUD process and six current graphics allocations. Reinitialization
includes the existing supervisor and renderer startup delays. The user observed
the screen go dark; transport recovery and physical recovery are distinct checks.

## Automated validation and distribution

113 focused host tests pass, one Linux-only test skips on Windows. Coverage
includes signed capability forgery/replay/identity rejection, legacy JPEG,
registration validation, auto encoder fallback, ordered reference queues,
bounded sender shutdown, decoder stop/off ordering, direct USB pacing, existing
performance guards, retry logging and graphics/GC cleanup. Two older test mocks
were updated to include the already-required graphics setup/teardown hooks.
The Wiki generator's expected catalog count is updated for the already-published
196th setting; H.264 adds no new catalog setting.

ESP-IDF 5.4.0 builds the 891888-byte app. The release packager validates the
N16R8 partition layout, app version, dependency hashes and compiled settings;
the public package excludes NVS and credentials. Browser flashing is a separate
workflow from the native UART app-only validation performed on this board.

The installer and Korean/English settings guides explain the one-time S3 1.2.0
update, preserved registration, H.264 selection and JPEG compatibility. Both
maintained branches receive the shared changes with single-parent commits.
