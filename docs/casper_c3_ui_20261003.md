# Casper EV C3 UI frame-rate analysis — 2026-10-03

Analysis only: no production code, affinity, priority, device settings or deployment changed.

## Conclusion

The strongest supported contributor is UI scheduling contention on core6,
amplified by higher path-overlay CPU work while driving. The expanded C3
affinity policy permits cores0,1,2,3,6, but every steady-state procLog sample
of the UI main thread still reports core6. Expanding the allowed mask has not
demonstrated effective load distribution in this drive.

Core6 averages 91.70% busy after startup; the UI main thread spends 584.52 ms
per second runnable but waiting. Core7 has the largest observed headroom,
followed by core4. This is evidence for a placement comparison, not proof that
moving UI will fix presentation or preserve every other workload.

## Current allocation and observed execution

`openpilot/selfdrive/ui/ui.py` selects `DisplayScheduler(6, include_little=True)`
on tici/tizi. `common/display_scheduling.py` applies cores0,1,2,3,6 and
SCHED_OTHER/nice19 to all UI threads every0.5 seconds onroad. Offroad uses
cores0..3. C4 retains its separate core6-only policy.

After t=10 s, UI PID47124 has 56/56 last-CPU samples on6, nice19 and priority39.
The kernel's isolated-core policy is a plausible reason a broad affinity mask
does not balance execution as intended, but the logs lack sched-domain/cpuset
readbacks and a complete thread migration trace. Do not claim that the live
mask is core6-only, or that absolutely no migration happened between samples.

The same core hosts controlsd/selfdrived (FIFO53), camerad (normal/nice0)
and camera IRQs by source policy. CPU means over the steady procLog interval:

| Process | One-core CPU % | Sampled main-thread CPU |
| --- | ---: | --- |
| UI, including workers | 33.48 | 6 |
| selfdrived | 26.96 | 6 |
| controlsd | 21.74 | 6 |
| camerad | 11.18 | 6 |

UI main-thread runtime diagnostics alone measure 29.82% CPU. Process CPU includes
workers and is not an exact per-core attribution. Both realtime controls run
before normal UI; normal camerad also has higher scheduling weight than nice19
UI. Nice19 alone is not a demonstrated root cause independent of placement.

and no running dmonitoringmodeld or USB cluster process. The light core7 load

## Other explanations and limits

After t=10 s all three camera streams and modelV2 remain approximately20 Hz,
with consecutive frame IDs. Maximum camera SOF intervals are55.31/55.39/55.45 ms
(road/wide/driver). ModelV2, cameraOdometry and livePose have no invalid messages;
livePose inputsOK/sensorsOK remain true. Therefore the sustained low UI FPS is
not explained by a simultaneous loss of camera/model publication rate.

Startup does have model readiness/initial history skips and transient invalidity;
this is excluded from the steady conclusion, not hidden as an all-route clean bill.
All247 thermal states are green, CPU temperature stays at or below61.4°C.
The logged GPU utilization is3% throughout, so there is no recorded GPU saturation
signal; these coarse samples cannot exclude short graphics synchronization stalls.
UI recording and plotMode are zero throughout. No CPU-frequency trace is available
to prove the absence of every kind of clock throttling.
