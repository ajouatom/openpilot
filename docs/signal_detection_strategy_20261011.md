# 신호등 원거리 검출 개선 조사와 실제 영상 비교 — 2026-10-11

## 결론

현재 가장 유망한 다음 후보는 **사전학습 신호등 신경망 + 해상도를 보존한 관심영역 + 물체 추적 + 최신 영상의 색상·화살표 판독**이다. 작은 자체 학습기나 수작업 색상 조건만 계속 조정하는 것보다 이 구성을 먼저 비교할 근거를 얻었다. 다만 이번 결과로 차량 제어에 사용할 수준이라고 결론내릴 수는 없다.

사용자가 제안한 주행경로 상단 집중과 중첩을 실제 자료로 검사했다. 상단 확대는 검출에 도움이 됐다. 과거 영상을 단순 평균하는 중첩은 전환 전 색상을 남겼다. 추가로 차량의 OS04C10 센서 입력을 현재 출력보다 높은 해상도로 활용할 수 있는 코드상의 조사 지점을 찾았다.

이 작업은 PC 오프라인 조사다. 차량 접속·설정 변경·프로세스 재시작·모델 교체를 하지 않았다. 기존 내부 주행 ONNX, x/v, 제어 로직은 그대로이며 마지막 확인 상태는 비교/표시 ON, assist OFF다. 이번 공개 모델을 재학습하거나 차량에 설치한 것은 아니다.

## 실제 비교한 자료와 모델

기존 개인 보관 자료의 수동 위치 표시 75장 중 `box_eligible`이고 정답 상자가 있는 73장을 평가했다. 모두 1344×760 영상이며 주간·역광·해질녘 장면이다. 각 영상의 **선택된 신호등 하나**에 대한 정답이므로, 화면 전체의 모든 물체를 표시한 검출 평가셋은 아니다. 서로 인접한 프레임도 포함되고 기존 개발 때 사용한 자료이므로 독립적인 73개 교차로 시험이나 완전한 미사용 평가셋으로 해석하지 않는다.

공개 Autoware 모델을 내려받아 ONNX Runtime CPU에서 실제 실행했다.

| 항목 | 고정한 모델 |
| --- | --- |
| 위치 검출 | YOLOX-s `tlr_car_ped_yolox_s_batch_1.onnx`, v3.0, 35,794,092 bytes |
| 검출 저장소 revision | `3f0616ffda0c19fc84fc455f988421c0df970e5d` |
| 검출 SHA256 | `1ad633066a1195006f4709f8fa07800dd65a74a814b3efb4c99bcc5a1a7962f6` |
| 상태 분류 | MobileNetV2 `traffic_light_classifier_mobilenetv2_batch_1.onnx`, v4.0, 8,926,508 bytes |
| 분류 저장소 revision | `527c4905afd8f1bfcc03253529a105f7fa5a6d36` |
| 분류 SHA256 | `455b71b3b20d3a96aa0e49f32714ba50421f668a2f9b9907c30b1346ac8a3703` |

모델 저장소는 Apache-2.0으로 표시되어 있다. 검출기는 일본 영상으로 학습된 공개 후보이며 한국 신호등·현재 카메라에 맞춰 재학습하지 않았다. Autoware 전체 파이프라인을 이식한 것도 아니다. [검출 모델](https://huggingface.co/AutowareFoundation/traffic_light_fine_detector/tree/3f0616ffda0c19fc84fc455f988421c0df970e5d), [분류 모델](https://huggingface.co/AutowareFoundation/traffic_light_classifier/tree/527c4905afd8f1bfcc03253529a105f7fa5a6d36).

검출 전처리는 BGR 0–255, 416×416 좌상단 배치/114 패딩, strides 8/16/32 YOLOX decode, vehicle-light score 0.3, 같은 클래스 NMS 0.65다. 보행자/배경 클래스를 제외한 분석용 어댑터로 원본 Autoware 전체 클래스 NMS와 완전히 같지는 않다. 두 타일의 결과는 평가에서 합쳤으며 타일 간 중복 제거는 아직 하지 않았다.

분류는 RGB, 비율 유지 224×224 좌상단 배치/검정 패딩, 공개 mean/std를 적용했다. 출력 합이 약 1인 확률 출력이므로 softmax를 다시 적용하지 않는다. 처음 수행했던 강제 정사각형 변형/추가 softmax 결과는 폐기하고 수정 후 재실행했다. [분류 전처리 구현](https://raw.githubusercontent.com/autowarefoundation/autoware_universe/main/perception/autoware_tensorrt_classifier/src/tensorrt_classifier.cpp), [RGB 입력 경로](https://raw.githubusercontent.com/autowarefoundation/autoware_universe/main/perception/autoware_traffic_light_classifier/src/traffic_light_classifier.cpp).

## 위치 검출 결과

IoU는 정답 상자와 검출 상자의 겹침 정도다. 아래 숫자는 선택된 정답 상자를 해당 겹침 기준으로 찾은 **영상 수**다.

| 방법 | IoU ≥0.3 | IoU ≥0.5 | PC 처리 중앙값 / p95 |
| --- | ---: | ---: | ---: |
| 현 수작업 후보 검출 `detect(daytime_cores=True)` | 58/73 | 49/73 | 6.6 / 8.2 ms |
| 신경망, 전체 화면 →416 | 68/73 | 63/73 | 83.6 / 88.1 ms |
| 신경망, 상단 관심영역 →416 | 73/73 | 68/73 | 83.4 / 87.7 ms |
| 신경망, 겹치는 두 관심영역 →각각416 | 73/73 | 70/73 | 166.7 / 173.3 ms |

상단 영역은 x=20–85%, y=4–60%의 고정 영역이다. 두 타일은 각각 x=18–58%, 45–85%, y=4–64%다. 이번 시험에서 경로·캘리브레이션을 이용하는 동적 관심영역은 아직 구현하지 않았다.

같은 신경망 입력 크기라 상단 한 영역은 전체 화면과 계산 시간이 거의 같지만 신호등에 더 많은 픽셀을 배정한다. 두 타일은 더 정확한 위치를 얻는 대신 검출기를 두 번 실행한다. 이 결과만으로 두 타일이 항상 최선이라고 할 수 없다.

특히 정답 상자가 **16×5 픽셀**인 네 장은 전체 화면 신경망과 수작업 검출이 모두 놓쳤고, 상단 신경망은 모두 IoU ≥0.5로 찾았다. 전체 화면 축소 시 16×5가 약 5×1.5 입력 픽셀에 불과하기 때문이다. 단, 먼 쪽 신호등을 찾았다는 사실이 현재 차량이 따라야 하는 신호등을 선택했다는 뜻은 아니다.

이 표는 전체 precision, AP, 잘못된 물체 검출률, 실제 신호등 색상 정확도, 최대 검출 거리를 제공하지 않는다. 영상에 표시되지 않은 다른 후보를 오검출로 일괄 계산할 수도 없다. 타이밍은 Windows PC, OpenCV 4.13.0, ONNX Runtime 1.23.2, 각 1 thread, 첫 영상 제외 값이며 **차량 처리 시간과 다르다**. 수작업 열은 추적·대기·전송 없이 검출 함수만 실행한 시간이다.

## 상태 판독과 기존 실패 구간

상단 검출기의 모든 후보를 분류하고, 평가 단계에서만 정답 상자와 가장 겹치는 후보를 골랐다. IoU ≥0.3로 대응한 결과는 다음과 같다.

| 수동 정답 | 신경망 출력 | 영상 수 |
| --- | --- | ---: |
| 적색 | `red` | 41 |
| 원형 녹색 | `green` | 5 |
| 원형 녹색 + 좌회전 | `green` | 26 |
| 원형 녹색 + 좌회전 | `left,red,straight` | 1 |

따라서 단순 원형 적/녹 대응에는 개선 후보로 볼 근거가 있지만 **화살표까지 맞췄다는 결과는 아니다**. 대부분의 좌회전 화살표가 출력에서 빠졌고 한 장은 적색 포함 조합으로 틀렸다. 이 모델의 11개 조합 클래스가 한국의 모든 조합을 표현하지도 않는다. 정답 상자를 직접 준 별도 조건에서는 녹색+좌회전 27장 중 두 장이 적색 포함 조합으로 틀렸다. 상자 위치에도 결과가 민감하다.

분류 122회 중 첫 회 제외 중앙값 6.4 ms, p95 7.3 ms/상자였다. 검출된 상자가 늘면 분류 비용도 증가한다. 출력 확률은 우리 영상에서 보정된 신뢰도가 아니므로 높은 숫자를 출발 허가 확률로 사용할 수 없다.

이전 재검증에서 녹색 확인이 안 되어 실패로 남겼던 `1094--10`의 822–854 프레임 중 10장을 별도로 검사했다. 기존 관찰기의 해당 상자를 직접 주면 새 분류기는 **10/10 `unknown`**, 새 상단 검출기도 해당 어두운 물체와 겹치는 후보를 만들지 않았다. 기존 수작업 방식이 raw green을 낸 840/844/847/851도 포함한다. 이는 해당 잘못된 녹색 증거를 피한 결과이며 실제 차량 정지/출발 문제를 해결했다는 시험은 아니다.

최근 `1096--37`에서도 69개 프레임을 추가 실행했다. 실제 녹색 전환 시 863에서 왼쪽 신호등 검출이 잠깐 빠졌고, 알려진 위치를 주면 분류기는 green이었다. 920–940의 다섯 표본은 왼쪽 등화가 어둡게 찍혀 검출을 놓쳤으며, 알려진 위치를 줘도 모두 unknown이었다. **새 검출기 역시 프레임 단위 소실이 있어 추적이 필요하다.** 같은 장면의 오른쪽 신호등은 더 잘 보였지만, 두 등이 같은 진행방향을 제어하는지는 별도 판단해야 한다.

## 중첩 실험과 권장 사용법

중첩에는 두 가지가 있다.

1. **공간적으로 겹치는 타일**: 원래 영상의 작은 영역들을 확대해 검사한다. 경계에 걸린 신호등을 놓칠 위험을 줄일 수 있다. 이번 두 타일 비교가 이에 해당한다. 실제 픽셀이 새로 생기지는 않는다.
2. **시간적으로 여러 프레임을 합치기**: 서로 다른 시점의 작은 위치 차이를 맞추면 노이즈 감소와 경우에 따라 추가 세부 정보 복원이 가능하다. 그러나 물체·차량 이동과 색상 전환을 처리해야 한다. RAW burst 기반 다중 프레임 초해상도 연구의 성과를 현재 압축 영상에 그대로 보장할 수는 없다. [Google 다중 프레임 초해상도 연구](https://research.google/pubs/handheld-multi-frame-super-resolution/).

최근 정차 영상에서 최신 프레임과 과거 네 프레임을 비교했다. 240×105 주변 영역에서 등화 부분을 제외한 배경으로 이동 정합을 수행하고, 상관계수 ≥0.8 / 이동 ≤5 px인 경우만 평균에 넣었다. 47개 검출 성공 시점의 과거 프레임 정합 188회는 모두 이 조건을 통과했고, 정합+평균 계산 중앙값은 PC 5.2 ms였다. 움직임이 작은 한 정차 구간의 결과이며 주행 중 정합 성능이 아니다.

**864 프레임의 최신 영상은 녹색인데, 과거 5장 평균과 정합 후 평균은 모두 적색으로 분류했다. 865에서야 녹색으로 바뀌었다.** 실제 전환은 862–863 사이이고 863에서는 자동 상자를 얻지 못했으므로, 이 비교에서 관찰한 추가 지연은 864→865 한 프레임(20 Hz에서 50 ms)이다. 전체 전환 지연을 정확히 50 ms라고 주장하지 않는다. 이것은 평균 합성 시험이며 초해상도 구현/검증은 아니다.

권장은 외형·위치 추적에는 짧은 과거 정보를 쓰되 색상은 최신 프레임과 시간 순서의 개별 증거를 보존하는 것이다. 기존 녹색을 밝기 최댓값으로 계속 남기거나, 사라진 녹색을 기억만으로 새 출발 허가로 만들면 안 된다. 상태 필터는 `관측됨 / 과거 상태 추정 / 판독 불가`를 구분하고, 반대 색의 새 증거를 즉시 평가해야 한다. 단순히 유지 시간을 늘리는 조정은 이번 결론에 포함하지 않는다.

## 현재보다 실제 픽셀을 더 얻을 가능성

최근 원본 rlog의 `roadCameraState.sensor`, `wideRoadCameraState.sensor`, `driverCameraState.sensor`가 모두 `os04c10`임을 확인했다. [센서 코드](../openpilot/system/camerad/sensors/os04c10.cc)는 입력 2688×1520과 `out_scale=2`를 지정하고, [출력 코드](../openpilot/system/camerad/cameras/spectra.cc)는 1344×760 버퍼를 만든다. 현재 fcamera 분석 영상은 이 축소 출력이다.

축소 경로에 `bps_fullres_dummy`라는 전체 해상도 출력용 placeholder가 있다. 따라서 **전체 해상도에서 상단 관심영역만 별도로 얻는 경로를 조사할 가치가 크다.** 다만 현재 이 버퍼가 소비자에게 공개되거나 프레임별로 안전하게 읽히는지는 검증하지 않았다. 공유 placeholder에 비동기 쓰기가 겹칠 수 있으므로 포인터만 노출하는 방식은 충분하지 않다. 완료 fence, 버퍼 수명/재사용, 별도 보관 또는 동기화된 crop, frame ID와 SOF/EOF 일치부터 확인해야 한다.

구현한다면 주행 모델의 기존 해상도·워프·노출은 유지하고 보조 검출기용 영역만 분리하는 방향을 우선 검토한다. 전체 NV12 영상은 패딩 제외 약 6.13 MB이므로 20 Hz 전체 복사는 약 123 MB/s다. 전체 복사/변환보다 필요한 영역을 제한하는 것이 중요하다. 이 대역폭 계산은 실제 추가 부하 측정값이 아니다.

두 배 선형 해상도가 두 배 검출 거리를 보장하지는 않는다. 렌즈, 초점, 흔들림, LED 노출, 포화, Bayer 처리, 색차 서브샘플링도 한계다. 지금 보관한 1344×760 파일을 확대해도 잃은 원본 픽셀을 그대로 복구할 수는 없다. 영상 중첩이나 센서 노출 변경에 앞서 **축소 전 픽셀 확보 가능성**을 우선 조사할 근거가 생긴 것이다.

## 다음 구현 후보

검출·추적·색상 판독을 다른 주기로 실행하는 구조를 우선한다.

- 전체 화면 또는 넓은 영역에서 새 물체와 주변 맥락을 주기적으로 확인한다.
- 경로·카메라 자세·기존 트랙을 이용해 상단 우선 관심영역을 정하고, 작은/불확실한 후보에만 추가 타일을 쓴다. 곡선·오르막·옆에 달린 신호·가까워져 화면 위로 나간 신호 때문에 고정 상단만 보지는 않는다. 기존 주행 모델의 경로는 우선순위의 근거 중 하나이며 절대적인 정답으로 사용하지 않는다.
- 신경망의 무거운 재검출 사이에는 작은 영역의 위치 추적과 색상·등화 상태 판독을 수행한다. 영상 관측 주기와 모델 계산 주기를 분리한다.
- 원형 적/황/녹, 꺼짐/판독불가, 화살표 방향을 분리한 한국 영상용 분류를 검토한다. 알려진 보행자등·간판·차량등을 음성 예제로 넣는다.
- 같은 교차로의 다른 신호, 다음 교차로 신호, 보행자등을 구분하고 내 진행방향과 연결한다. 위치를 찾는 능력과 차량 제어에 사용할 신호 선택 능력을 따로 검사한다.
- 객체 ID의 유지와 색상 확정/만료를 분리한다. 실제 카메라 시간과 결과 지연을 기록하고, 무거운 구형/신형 검출기를 매번 직렬 실행하는 현재 비교 비용을 상용 실행 예산으로 가정하지 않는다.

초기 성능 목표로 재검출 5 Hz 안팎, 작은 영역 관찰은 카메라 20 Hz를 따라가는 구성을 검토할 수 있다. **목표일 뿐 C4 달성 수치가 아니다.** 먼저 현재 모델 그대로 차량 외 환경에서 품질을 확인하고, 정차 시 별도 작업으로 실제 C4 지연·코어 부하·modeld/camerad 영향을 측정한다. 무거우면 가속기 지원 또는 작은 학생 모델/양자화를 비교하되 작은 신호 손실을 다시 검증한다. 사용자가 내부 장치 시험을 원했으므로 eGPU/외부 장치 추가를 전제하지 않는다.

이 설계는 신경망 위치 검출과 시간적 상태 필터를 결합하는 연구 방향과 맞는다. 다중 카메라를 쓴 aUToLights도 객체 검출 후 지도 사전정보와 상태 필터를 결합한다. 여기서는 그 논문의 지표나 실시간 성능을 달성했다고 주장하지 않는다. [aUToLights 논문](https://arxiv.org/abs/2305.08673).

작은 영역만 보는 방식에도 한계가 있다. Autoware 측에서도 국소 crop이 도로/차량 맥락을 잃고, 순차 ROI 처리에 지연이 생기는 문제를 지적했다. 그래서 상단 확대와 넓은 화면 확인을 함께 유지하는 구성을 제안한다. [Autoware 검출 구조 개선 논의](https://github.com/autowarefoundation/autoware_universe/issues/9719).

## 학습·검증을 진행할 순서

1. 이번 공개 모델을 기준선으로 고정하고 기존 전체 실패 구간의 연속 영상 평가를 확장한다. 이번에는 73개 정답 상자, 최근 69 프레임, 과거 실패 10 프레임을 실행했다. 이전 37개 세그먼트 전체를 새 신경망으로 재실행한 것은 아니다.
2. 기존 자료에서 모든 관련/비관련 신호등, 간판·차량등 같은 혼동 물체, 색 전환 앞뒤, 가림과 판독불가를 표시한다. 신호등 위치·색상·화살표·내 진행방향 관련성을 별도 정답으로 둔다. 이 구분 없이 x/v를 색상 정답으로 쓰지 않는다.
3. 날짜·교차로·주행 단위로 학습/검증을 분리해 사전학습 보조 모델을 미세조정한다. 인접 프레임을 무작위로 나눠 점수만 높이는 것을 피한다. 원래 주행 ONNX의 정지선 학습을 지우는 과정이 아니다.
4. 검출 거리 대신 우선 신호등 픽셀 크기별 누락, 잘못된 녹색, R→G/G→R 각각의 지연, 화살표 혼동, 트랙 교체, stale 결과, CPU/열 부하를 측정한다. 제어 연결 전에는 기존 실패/지연 주입 사례를 다시 통과해야 한다.
5. 최대 거리의 수치는 실제 등 위치와 카메라 자세/거리 기준이 있는 구간에서 측정한다. `최초 물체 검출`, `색상 확정`, `내 진행방향 신호 확정`을 별도로 보고한다. 과거 적색 요청부터 정지까지 약 106 m 이동했다는 값은 신호등까지 거리나 최대 검출 거리로 사용하지 않는다.

당장 무작정 영상을 더 모으는 것보다 **이미 모인 자료로 사전학습 신경망과 해상도 활용을 먼저 검증하는 것이 우선**이다. 추가 촬영은 비·완전 야간·곡선/경사·원거리·황색/화살표·신호 없는 도로 등 현재 부족한 조건과 실패 구간에 집중하면 된다. 지금 자료만으로도 후보를 비교하고 개선을 시도할 수 있지만 모든 조건의 차량 안전성을 확정할 수는 없다.
