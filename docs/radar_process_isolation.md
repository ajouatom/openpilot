# Radar preprocessing isolation and equivalent-output optimization

## Current CPU placement

The September 22 user-approved grouping keeps radarcan on core4 FIFO51 and
radard on core5 FIFO51, moves planner to core4 FIFO51 and card to core5 FIFO53,
and leaves camera/IRQ on core6. Controlsd/selfdrived stay core4 FIFO53 and
model/DM stay core7. See [camera placement measurements](camera_core5_trial.md)
for parked C4 timing gains and increased planner/radar latency. The historical
core6-sharing motivation below predates this grouping. Radar algorithms,
batch joining, replay outputs and priorities are unchanged by the grouping.

## Motivation and scope

The September 2026 EV9/C3 and Ioniq5/C4 investigations found card and camerad
sharing core6. card runs FIFO53 and consumed about 73% of a core in both
segments; camerad uses normal scheduling. Core6 averaged 84%/80%. This is a
credible source of scheduling interference, not proof of the cause of every
camera/IFE error. No camera validity checks or error alerts are relaxed.

`card` retains vehicle CAN decoding, carState publication, and actuator CAN
transmission. A separate `radarcan` process owns RadarInterface and liveTracks.
It runs on core4 at FIFO51, below controlsd/selfdrived FIFO53. Core4 averaged
52–54% in these samples; placement still requires C3/C4 device validation.
The existing model-driven radard and planner stay on core5. The planner's
existing same-track fast update is retained, so it does not have to wait for
model fusion after every new radar frame. There is one liveTracks publisher.

## Input ordering and failures

Each carState contains radarInput: the first/last CAN Event timestamps, CAN
packet count, and card's monotonic receive timestamp. radarcan subscribes to
both CAN and carState without conflation, joins the exact batch to vEgo/aEgo,
and calls update_carrot once per carState tick, including empty CAN batches.
This preserves ego-history indexing and radar trigger cadence; using whichever
carState happened to arrive first would not. Receive time replaces wall clock
for interval estimation, so wall-clock adjustments cannot change radar dt.

Incomplete batches wait for the other socket. Missing packets, invalid
metadata, state overflow, input age over 100 ms, and CAN/ego input loss publish
invalid liveTracks with canError. Processing that itself exceeds the age bound
also invalidates. After a gap, RadarInterface is rebuilt so old IDs and filters
cannot bridge missing input. Input queues are bounded; publishing an error is
rate-limited to 20 Hz. A crashed process remains covered by manager supervision.

The replay card records its input CAN timestamp instead of host execution time.
The radarcan process replay must use carState regenerated by the matching card;
old recorded carState lacks exact batch boundaries. This limitation is explicit
in its process-replay configuration. Older recorded logs remain readable.

The change adds one Python process and duplicates CAN envelope decoding; total
CPU/memory reduction is not assumed. Its primary purpose is moving radar work
off core6 without coupling CAN parsing to model-fusion duration.

## Equivalent-output optimization

The controller uses RadarMotionPredictor only for the selected primary's
cut-out probability. Its production-only compact mode retains the existing
association, all track histories, occupancy latches, motion estimates and
the same horizon/occupancy probability arithmetic. It omits unused CUT-IN
scores, diagnostic trajectories and history output. The full predictor remains
the default for review tools. TrajectoryCutInDetector remains responsible for
production cut-in decisions. Its pairwise median estimator is unchanged;
timestamp and value attributes are extracted once before the same pair loop.

## Validation performed locally

- 879 focused detector/controller/replay/planner/vault tests passed. This
  includes 12 new exact-probability/internal-state comparisons across sources,
  sides, curves, lead handoffs, ID swaps and dropouts, plus CAN batch-order,
  missing-packet, empty-tick, timeout and bounded-buffer checks.
- An additional 291 radar lead-filter and group3 preprocessing tests passed.
- The full maintained corpus contains 95 logs and 492 labelled items per mode.
  Mode 2 and mode 3 reports compare exactly with pre-change d2973b3ff8. Existing
  expectation failures remain 10 / 13, with 0 / 1 pre-deceleration failures and
  208 unverified items due to insufficient labelled input. No logs are missing;
  this is a no-new-failures comparison, not an all-pass corpus claim.
- Production controller outputs compare exactly across all 1,197 usable EV9
  frames and 1,196 Ioniq5 frames, including all lead/list fields.
- Real CAN/ego replay compared direct RadarInterface calls to independent
  stream joining: EV9 6,001 batches / 1,200 radar outputs; Ioniq5 5,998 batches /
  1,198 outputs. All output values agree, including missing-value NaNs. Because
  old logs lack drain metadata, both paths use identical reconstructed
  boundaries; this does not claim reproduction of the old liveTracks schedule.
- PC controller mean time in one paired replay: EV9 1.372 -> 1.270 ms (7.4%);
  Ioniq5 1.014 -> 0.923 ms (9.0%). Host timing is not a C3/C4 speedup guarantee.

Build CI additionally exercises the real radarcan process and IPC on Linux:
startup, valid publication, missing claimed CAN, empty CAN timeouts, recovery,
and complete input loss. Native process replay checks use card-generated
metadata. These checks require the built runtime unavailable on Windows.

## Deployment and device follow-up

Shared changes deploy through the Carrot Routes image workflow and existing NAS
scheduled updater. The source fingerprint includes the changed predictor and
schema. Confirm the intended sourceCommit, updater verification, an actual
upload-result page and recalculated radar before reporting server completion.

`runtimeTiming` now includes card, radarcan and radard. Inspect stage wall/CPU
time, input age, pending queues, invalid inputs, core4/core6 load, camera cadence
and IFE errors alongside the unchanged planner fast-path diagnostics. The
baseline active track-publication-to-plan mean was about 5.7 ms. Compare p95,
p99 and maximum delay, not just average CPU. C3/C4 on-device camera improvement,
thermal behavior and closed-loop vehicle response remain unvalidated until
new logs are received.

No user setting, radar threshold or model artifact is changed.
