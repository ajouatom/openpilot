# RAV4 TSS2 2022 cruise investigation — 2026-10-09

## Evidence and scope

The user reported an apparent conflict with Toyota radar whenever longitudinal
cruise was enabled and requested investigation and correction. Examined full
cereal-schema rlogs for route `00000007--2aed99af58`, segments 10–14, recorded on
`6eeb19999f`; segment 11 qcamera and the two supplied-day settings snapshots were
also inspected. Raw logs, video, settings and reproduction scripts remain local
under `.analysis/archive/2026-10-09-rav4-acc/`.

The recorded CarParams select `TOYOTA_RAV4_TSS2_2022` by fixed fingerprint, with
no firmware inventory, Toyota flags 1372, `openpilotLongitudinalControl=true`,
`pcmCruise=true`, `radarUnavailable=true`, and safety parameter 73. This is the
existing radar-ACC experimental-longitudinal path: `DISABLE_RADAR` is set and
tester-present traffic maintains the disabled radar transmitter. It is not a
recording of stock ACC speed-button control. Fixed selection is not independent
firmware verification of the car variant.

## Observations

- All 30,010 carState samples have valid CAN, no reported `accFaulted`, and no
  steering fault. Stock-AEB/FCW booleans remain false, but AEB decoding is disabled
  in this configuration, so this does not demonstrate available stock AEB.
- All 2,809 Panda samples have no faults, no safety RX invalidity, no TX block,
  and no new CAN error/loss counters. Existing cumulative counters remain fixed.
- There are 10,003 host `ACC_CONTROL` (0x343) messages and 10,003 TX echoes.
  No original RX 0x343 is present on bus 0 or 2. About 5 Hz diagnostic
  tester-present traffic continues. The recording does not show competing stock
  acceleration commands or a failed radar-disable session during these segments.
- Cruise is enabled only in segment 11, 5.880–27.691 s. Pedal override delays
  longitudinal activation until about 7.594 s; total `longActive` is 1,956 frames,
  approximately 19.56 s. Cruise turns off without a host cancel request.
- Vision supplies the lead. The forward video shows traffic ahead; the initial
  lead distance is about 27 m at 75 km/h, and the selected following target is
  longer. Some initial deceleration is therefore expected from the planner.
- A separate raw `PCM_CRUISE_SM.TEMP_ACC_FAULTED` bit is set in six received
  messages, 45.637–50.757 s, and clears at 50.947 s. It starts just after the main
  switch is turned back on, well after longitudinal cruise stopped. The ordinary
  `PCM_CRUISE_2.ACC_FAULTED` remains zero. This transient is not explained or
  claimed fixed here; no warning bit is suppressed or safety check relaxed.

## Confirmed software mismatches and correction

### Toyota mode did not consume the PCM set speed

Both settings snapshots select `SpeedFromPCM=3` (Honda/Toyota). Previously,
`VCruiseCarrot` consumed the stock set speed only for mode 1. Toyota does not
publish physical RES/SET as speed `buttonEvents` here, so mode 3 retained a
separate stale Carrot speed. In this recording the PCM control set speed is
75 km/h (cluster set speed 81 km/h), while Carrot's target remains 83 km/h.
Later the PCM control set speed changes to 74 km/h (cluster 80 km/h) but Carrot
still retains 83 km/h. The 75 value is an ECU control value, not a claim that
the dashboard displayed 75.

Toyota/Lexus mode 3 now uses `cruiseState.speed` for the base control target and
`speedCluster` for the displayed set speed, as mode 1 already does. Modes 0/2,
Honda mode 3, non-PCM vehicles, engagement, and the stock/openpilot-longitudinal
selection remain unchanged. Lead/navigation/curve planning can still lower the
target. No PCM button messages or radar detection policy are added.

### Duplicate acceleration correction

Recorded Toyota CP has outer Kp=0, Ki=0, Kf=1, and its vehicle CarController
already closes an acceleration loop at the 33.3 Hz PCM transmission rate.
However, common LongControl replaced those outer gains with saved
`LongTuningKpV=100`, `LongTuningKiV=0`, `LongTuningKf=100`, then applied another
acceleration-error correction. This fed measured-acceleration variation back
into the input of the existing Toyota compensator.

Toyota/Lexus now fix the common outer controller at Kp=0, Ki=0, Kf=1 from
construction and through every settings refresh. The three ineffective gain
settings are hidden for brand `toyota`; stored values are retained. Existing
Toyota inner compensation, pitch handling, acceleration/rate limits,
PERMIT_BRAKING, stopping, disengagement, radar-disable traffic, and Panda safety
are unchanged. Hyundai's fixed gains and other brands' adjustable gains remain.

This restores the separation already implied by the recorded CP and the local
Toyota CarController. The [upstream Toyota controller](https://github.com/commaai/opendbc/blob/master/opendbc/car/toyota/carcontroller.py)
also owns acceleration compensation; this change does not import its unrelated
newer pitch/stop behavior.

## Validation and limits

- 422 focused desktop tests pass: Toyota target/limit/stop/inactive and settings
  refresh, PCM SET/RES tracking and unaffected modes/brands, Hyundai tuning,
  stopping, coasting, buttons and settings schema. Windows substitutes Params
  storage and hardware imports. Six broader engagement tests requiring native
  messaging were excluded after failing on missing Windows `msgq`; they do not
  exercise the changed speed-selection branch.
- Same-input controller comparison covers all five segments. The 1,956 active
  input frames retain the logged planner targets, ego measurements and timing;
  only the duplicate outer correction is removed. Maximum removed correction
  is 0.348 m/s². Input-command consecutive-step RMS changes from 0.0260 to
  0.00266 m/s²; the target/request sign differs on 278 original frames versus
  zero with target pass-through. Some sign reversal is legitimate feedback in
  general; these counts describe the redundant outer loop, not a universal
  safety criterion.
- Running both command sequences through the unchanged Toyota CarController
  gives consecutive-step RMS 0.0325 → 0.00288 m/s². No non-ACC CAN messages or
  inactive ACC transmissions differ. This is an input replay with desktop
  scheduling and segment-start state, not an exact reconstruction of every
  logged physical TX timestamp.
- The speed correction is separately checked against PCM values and synthetic
  SET/RES sequences. The planner is not recomputed with the lower target in the
  controller comparison. Neither replay predicts the revised vehicle speed,
  stopping clearance or closed-loop comfort. Actual RAV4 driving, the transient
  ACC state bit, and other Toyota/Lexus vehicles remain unvalidated.
