## PR564: integrate GPS process isolation

Reviewed [PR564](https://github.com/ajouatom/openpilot/pull/564), head
`9d2a435ed332e0d5cde663a69be6c60e99e7e43c`. Select the existing
`PythonProcess(spawn=True)` path for `qcomgpsd` so its startup/restart does not
fork the running manager with its live IPC state. Keep TICI eligibility, the
onroad/external-GPS predicate, process supervision, and control checks unchanged.

The GPS assistance worker is a module-level target and its Event is created
inside GPS main. Code review found no local target or inherited manager object
required by this path. The GPS parser, modem I/O and assistance code are unchanged.
Import the contributor's lifecycle regression extension for both `carrot_man`
and `qcomgpsd`: actual child creation, crash/restart, duplicate-start prevention,
stop, fork callbacks and parent-only state inheritance. These tests substitute
the service body with a harmless worker; they do not run the physical modem.

Before the production change, the new spawn-selection regression failed on
Windows. After the change, focused process lifecycle, crash reporting and
existing USB power tests passed: **49 passed, 4 POSIX-only skipped**. Windows
already uses spawn by default, so its runtime test alone cannot distinguish the
old Linux fork path. The Linux startup-recovery workflow provides that comparison.
The contributor's ARM/parked-device results remain contributor evidence, not a
new hardware validation performed here. Neither the serial exception's physical
cause nor every possible manager stall is resolved by this bounded change.
