## 표시 revision 3

`SignalDisplayReader`에 표시 전용 `DisplayContinuity`를 추가했다.

- 정상 카메라가 계속 갱신되는 동안, 다음 결과를 기다리거나 트랙을 잠깐 놓치면 마지막 위치·색상을 **촬영 시각 기준 최대0.8초** 표시한다. 같은 파일을 다시 읽는 것으로 시간을 갱신하지 않는다.
- 유지한 표시는 어둡게 그리고 `R~ / G~ / ?~`, `~ 이전 판독`으로 구분한다. 유지 상태를 새 확정 판독으로 표시하지 않는다.
- 같은 ID에 새 red/green이 들어오면 즉시 교체한다. 새 unknown은 잠깐 이전 색을 표시할 수 있지만 색의 마지막 관측 시각을 갱신하지 않아 오래된 녹색이 무한 연장되지 않는다.
- 알려진 ID의 새 위치는 반영한다. 같은 위치에 다른 ID가 생기면 겹치는 이전 상자를 제거한다. 보관은20개 이하이며 시간 경과로 지운다.
- 카메라 정지/오래된 이미지, wide/다른 해상도, 잘못된 레코드, 작업 세션 교체, 표시 OFF는 기억을 비운다. 화면의 카메라 자체는 여전히350 ms 이내여야 한다.
- 기존 `visible_tracks()` 기본 호출의 엄격한 시간 조건은 유지한다. 연장된 기억은 표시 경로에만 있다. 제어의200 ms freshness, observer 상태, red_sign/출발 조건과 original ONNX에는 연결하지 않는다.

0.8초는 검출이 늦게 도착하는 사이의 빈 표시를 줄이기 위한 표시 수명이며, 신호가 계속 안 보이는 상황까지 영구 유지하는 설정이 아니다. 실제로 사라진 물체나 잘못된 후보도 잠시 남을 수 있고 이전 상자의 위치가 현재 영상과 어긋날 수 있다. 그래서 유지 표시를 구분한다.

26개 구간의 관측 도착 시각과 road frame 시각을 재생했다. 카메라 표시 지연50 ms, UI10 Hz, 시작 위상10가지를 가정하면 하나 이상 상자를 표시하는 샘플은 기존28.2–29.7%에서 새74.3–74.5%로 증가한다. **실제 USB 패널의 깜박임 측정이나 인식 정확도 증가가 아니다.** 오래된 후보를 표시하므로 비율이 증가하는 것은 의도한 동작이며, 오검출 역시 잠시 유지될 수 있다.

## 상단 신경망 + 빠른 추적

`tools/signal_analysis/neural_signal.py`는 [앞선 조사](signal_detection_strategy_20261011.md)의 고정된 Autoware YOLOX-s/MobileNetV2 해시를 확인하는 오프라인 reference다. ONNX Runtime CPUExecutionProvider, 한 thread다. 기존 서비스/Params/메시징에 연결하지 않는다.

고정 상단 영역에서 신경망으로 찾고, 사이 프레임은 등화 내부를 제외한 주변 형태의 template로 위치를 추적한다. 색상·화살표 조합은 매 프레임의 **현재 crop**에서 분류한다. 추적은 신경망 재확인 없이0.5초가 지나거나 영상 지지가 약하면 끝낸다. 색상 기억으로 판독을 만들지 않는다. 초기에는 약5 Hz 재검출을 썼고, 소실 후 재획득 지연을 확인한 뒤 최종 후보는 추적 대상이 없으면10 Hz로 탐색하도록 바꿨다. 부동소수점 경계 때문에 탐색 주기가 밀리지 않도록 처리했다.

1098--6 원본 HEVC의600–980, 연속381프레임에서 매 프레임 신경망 검출+분류와 비교했다.

| 최종 비교 | 매 프레임 검출 | 검출+추적 후보 |
| --- | ---: | ---: |
| 신경망 검출 호출 | 381 | 105 |

초기 후보는 평균25.8 ms였지만 녹색 첫 출력이874로150 ms 늦었다. 소실 시 탐색을 빠르게 하면서 평균 계산 비용은33.4 ms로 늘고 이 지연은 없어졌다. **정확성/응답을 위해 계산을 더 쓴 최종 선택**이다. 두 실행의 PC 부하가 완전히 같지는 않아 반복 간 소수점 시간 차이는 비교하지 않는다.

수동 crop 검토에서는810–824에 적색이 보이다 점점 약해지고,830–870의 많은 이미지에서 등화가 거의 보이지 않으며871에 원형 녹색+좌회전이 뚜렷해진다. 최종 후보 출력은600–824 red,825–834 unknown,835–870 상자 없음,871–980 green이다. **어두운 구간의 검출 문제는 해결되지 않았다.** 원형 녹색만 출력하며 좌회전 화살표까지 정확히 출력한 것도 아니다. 한 정차/출발 사례 결과를 전체 시간대의 정확도로 확대하지 않는다.

평균 계산량은 약67% 줄었지만 무거운 검출 프레임의 p95는 여전히50 ms보다 길다. 그러므로 이 동기식 PC 시퀀스 시험을 실시간20 Hz나 C4 실행 성공이라고 부를 수 없다. 장치에서는 오래된 입력을 쌓지 않는 별도 추론 스케줄링과 실제 지연/부하 시험이 필요하다. 현재 차량의 검출 방식과 주기는 이 코드로 바뀌지 않았다.

## crop 구현과 고해상도 연결의 구분

같은 모듈의 `copy_nv12_crop_rgb()`는 NV12의 Y/UV 평면에서 짝수 경계의 필요한 영역만 복사하고 RGB로 바꾼다. 패딩/UV offset을 처리하며, 같은 버퍼 전체를 RGB로 변환한 뒤 crop한 결과와 픽셀 단위로 같은지 검사했다. 호출자가 프레임 완료/버퍼 재사용을 확인해야 한다.

2688×1520 가상 NV12 버퍼를 사용한 복사/변환 시험은 다음과 같다. 실제 고해상도 센서 영상 검증이 아니라 메모리 경로/계산 비용 시험이다.

| 영역 | NV12 bytes/frame | 전체 대비 | PC 변환 중앙값 |
| --- | ---: | ---: | ---: |
| 전체2688×1520 | 6,128,640 | 100% | 5.25 ms |
| 상단1746×852 | 2,231,388 | 36.4% | 1.84 ms |
| 작은640×320 | 307,200 | 5.0% | 0.07 ms |

작은 영역은20 Hz에서도 NV12 약6.14 MB/s이므로 사용자가 제안한 영역 제한은 유효하다. 하지만 센서 읽기/ISP의 원래 처리 비용까지 이 비율로 없어지는 것은 아니다. 같은416×416 입력을 사용하면 신경망 한 번의 계산량도 거의 그대로다. 영상 복사·변환, 신경망 호출 횟수, 판독 대상 수를 함께 줄여야 한다.

**축소 전2688×1520 camerad 버퍼에서 이 crop을 얻는 연결은 아직 구현하지 않았다.** 현재 새 주행 비교는1344×760 녹화본이다. `bps_fullres_dummy`를 실제 소비자에게 제공하려면 완료 fence, 쓰기 중 재사용, 프레임별 보관을 해결해야 한다. 동적 경로 기반 영역 선택도 아직 고정 상단 ROI와 구분한다.

사용자가 질문한 GPU 활용 역시 별도 단계다. 이번 reference는 CPU이며, 내부 주행 모델은 기존 tinygrad/QCOM 경로를 사용한다. 저장소에 `OnnxRunner`와 QCOM 입력 경로가 있어 이식을 조사할 수 있지만 이 신호등 모델의 연산 지원·출력 동등성·장치 지연·동시 실행 영향은 검증하지 않았다. 외부 eGPU 추가를 전제로 하지 않으며 GPU가 항상 전체 지연을 줄인다고 가정하지 않는다.

차량 설치 스크립트는 fresh offroad 또는 비활성 Park를 확인하고 이 작업과 선행 문서의 제한된 경로만 fast-forward한다. 기존 ONNX 해시, assist OFF, 주요 주행 프로세스 PID를 보존한다. offroad이면 재부팅/프로세스 재시작 없이 다음 실행에 적용하고, Park에서 표시가 실행 중이면 표시 프로세스만 재시작한다. 실제 설치/화면 실행 확인 여부는 비공개 `deployment.json`에 기록하며, 원래 모델과 새 보조 신경망을 혼동하지 않는다.
