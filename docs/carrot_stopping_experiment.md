# CAN FD 정지 제어: carrot-stopping 시험 및 carrot-wip 반영

`carrot-wip`의 `c04fa4566c`에서 분리한 `carrot-stopping`의 정지 제어를
2026-09-17 사용자 요청으로 `carrot-wip`에 반영했다. 현대·기아 CAN FD의
openpilot 종방향 SCC 송신 경로 두 곳(camera SCC / 일반 CAN FD)에만 적용한다.
일반 CAN, 순정 종방향 제어, 모델 선택은 변경하지 않는다. 별도 시험 브랜치는 삭제하며,
이후 코드는 `carrot-wip`에서 관리한다. 2026-09-23 사용자 요청으로 `CanfdStopRetry` 설정을
메뉴·카탈로그·Params 등록에서 제거하고 해당 CANFD 종방향 경로의 기본 동작으로 전환했다.
이전 저장값은 읽지 않는다. 같은 날 정지 충격 보고와 사용자 요청에 따라 조기 정지 판단,
양방향 -0.5 수렴 및 소프트홀드 준비 단계를 제거하고 기존 정지 제어를 복원했다.
`StoppingAccel`은 기본 -50, 범위 -100~-50, 단위 10으로 복원하며 모든 브랜드의
LongControl에서 초기화 시 및 매 100 제어 주기에 읽는다. 제어에서도 범위를 제한한다.
CANFD 한 번의 재시도와 상태 이력, 기존 인터록은 계속 기본 적용한다.

이 코드는 ECU의 정지 제어 진입 조건과 aReq 우선순위를 조사하기 위한 실험이다.
추돌 방지나 실차 정지 성공을 보증하지 않는다. 공개도로 적용 전 제동을 직접
인계할 수 있는 폐쇄 구간에서 실제 반응을 검증해야 한다.

## 송신값

| 단계 | StopReq | aReqRaw / aReqValue | Upper / Lower |
| --- | ---: | --- | --- |
| 저속 정지 요청 / 재요청 / 정지 유지 | 1 | LongControl 요청 / 기존 송신 제한 적용 값 | 0 / 0.20 |
| 복구 감속 / 재시도 실패 후 감속 | 0 | 음수 요청 / jerk 제한된 음수 값 | 0 / 0 |

InfoDisplay와 byte7(ZEROS_7)은 모두 0으로 보낸다. byte7=1은 Ioniq 5 PE 순정
측 로그에도 있었으므로, 0이 모든 차종의 정답이라는 의미가 아니다. Lower=0.20은
EV6 순정 측에서 관측한 고정 시험값이다. 순정 SCC가 켜져 있는지와 관계없이 같은
시험값을 쓰며, 실시간 순정 Lower를 복사하지 않는다. 정지 스위치라는 의미도 아니다.

현재 StopReq=1에서는 LongControl의 aReqRaw와 원래 패킷 경로의 aReqValue를 사용한다.
고정 -0.5 수렴을 CAN에서 다시 적용하지 않는다. LongControl은 실제 aEgo > StoppingAccel일 때
정지 단계에 진입하며 기존 근접 선행차/starting 상태 예외도 복원한다. 정지 출력은 목표보다
약할 때만 CP.stoppingDecelRate로 더 음수로 바뀌며 이미 강한 요청은 유지한다.
소프트홀드는 CP.stopAccel을 사용하고 별도의 음수 두 프레임 준비 없이 정지를 요청한다.
일반 CANFD 경로의 이전 raw 목표와 실제 value 출력 기록은 유지해 복구 jerk 계산에 사용한다.
설정을 더 약하게 바꿔도 이미 강해진 정지 출력은 즉시 풀리지 않는다.

복구 aReqRaw는 기존 요청과 -0.5 m/s² 중 더 음수인 값이다. 기존 가속도 한도는
CarController에서 유지한다. aReqValue는 실제 이전 시험 출력에서 기존 jerk 범위로
감속하며, 복구 중 양수 값은 보내지 않는다. 이 방식으로도 ECU가 요청을 따르지 않거나
감속이 부족할 수 있다. 음수 요청 유지 자체를 정지 성공으로 판정하지 않는다.

## 상태 전환과 시험 임계값

- shouldStop은 기존 플래너의 action_t와 그 1초 뒤 목표 속도 및 혼합 모드의 모델 판단을 따른다.
  별도 조기 정지 예측은 제거했다. controlsd는 갱신한 longControlState를 같은 주기에 게시한다.
- 아래 속도·시간·거리 임계값은 기존 재시도 한계로 유지하며 StoppingAccel 설정과 별개다.

- 속도가 0.7 m/s(2.52 km/h)를 넘으면 StopReq를 켜지 않고 음수 요청으로 접근한다.
- 속도는 vEgo, vEgoRaw, 네 바퀴 속도 절댓값 중 최댓값을 쓴다.
- 최초 StopReq=1 이후 속도가 0.10 m/s를 넘으며 0.6초 동안 0.03 m/s의 추가 감소가 없으면 복구한다.
- 0.5 m 이상 이동했고, 속도가 0.10 m/s를 넘으며 0.3초 동안 같은 감소가 없을 때도 복구한다.
- 정상 감속의 정지 직전 구간을 토글하지 않도록 낮은 속도에는 여유를 둔다. 다만 3초 후에도
  0.05 m/s를 넘으면 복구한다. 정지 요청 중 0.7 m/s를 넘으면 즉시 복구한다.
- 복구 시 StopReq=0으로 최대 1초 동안 감속 요청을 보낸 뒤 한 번만 StopReq=1로 재진입한다.
  그 전에 정지가 확인되면 즉시 정지 유지 요청으로 돌아간다.
- 재진입 후에도 위 조건으로 움직임이 지속되면 StopReq=0 감속을 유지한다. 주기적으로 토글하지 않는다.
- 속도가 0.05 m/s 이하로 0.2초 유지되거나, AVH_Sta=1이고 속도가 0.10 m/s 이하이면 정지로 판정한다.
  정지 유지 후 0.10 m/s를 넘는 움직임이 0.2초 지속되면 복구한다. AVH 신호 하나만으로 움직임을 무시하지 않는다.
- 크루즈 해제, 운전자 가속/제동(위 정차 소프트홀드 예외 제외), 오토홀드 인터록, 주차브레이크, 유효하지 않은 CAN/속도,
  전진 기어 이외 상태에서는 복구를 해제한다. 출발 요구로 stopping 상태가 끝나면 상태와 재시도 횟수를 초기화한다.

시간과 거리 임계값은 OEM 규격이 아니라 시험용 가정이다. 속도 센서 검출 한계와 노면,
차종별 제동 특성까지 보장하지 않으며, 추가 실차 자료로 검토해야 한다.

## 분석할 로그

`carrot_stopping` 이벤트에 이전/현재 단계, 전환 사유, 감지 속도, aEgo, AVH 유지 상태,
재시도 여부, 소프트홀드 여부, StopReq와 두 aReq를 남긴다. carlog는 card의 cloudlog 전달 경로를 사용한다.
기존 sendcan/반환 CAN, carState, ESC/AVH와 함께 확인한다.

1. StopReq=1에서 기존 음수 가속도 경로를 유지할 때 ESC가 완전 정지 제어를 수행하는가?
2. StopReq=0 이후, 재요청 이전부터 감속이 증가하는가?
3. 다시 1을 보낸 뒤에만 반응이 달라지는가?
4. 같은 입력에서 Lower=0과 0.20의 차이가 있는가? 현재 조합 전체의 성공만으로 Lower가 원인이라고 결론내리지 않는다.

제조사 공개 자료는 [모비스 정지 제어 특허](https://patents.google.com/patent/KR20140071120A/en)와
[현대·기아 가속도 제어 밴드 특허](https://patents.google.com/patent/KR102762189B1/ko)를 참고했다.
이는 실제 EV6 ECU의 구현·진입 조건·CAN 신호 우선순위를 공개한 사양서가 아니다.

## 검증 범위

상태 전환, 재시도 제한, 복구 중 강한 감속 요청 유지, StoppingAccel 범위·실시간 갱신, 기존 정지 감속 및 소프트홀드 출력과의 일치,
실제 CAN 패킹 및 OEM 정의의 비트 위치,
페달/크루즈/오토홀드/주차브레이크/CAN 오류 인터록을 단위 테스트한다.

초기 aReq=0 시험에서는 기존 EV6 원본 로그 3개를 full cereal로 읽어 기록된 차량·바퀴 속도와 AVH 상태를 재생했다.
정상 정지 구간은 토글 없이 정지 유지로 전환됐다. 실패 구간에서는 정지 요청 약 0.95초 후
StopReq를 해제하고 약 1초 후 재요청했으며, 계속 움직이는 기록에 대해 감속 유지로 전환했다.
이는 **기록된 입력에 대한 코드의 상태 전환 확인**이다. 명령을 바꿨을 때의 실제 차량 반응이나
제동거리, 사고 방지 효과를 시뮬레이션한 결과가 아니다.

2026-09-21 조기 정지 준비 변경은 K8 실패 기록의 고정 입력으로도 비교했다. 같은 재생 시계에서
shouldStop은 51.431초에서 50.482초로 앞당겨졌고, aEgo가 -0.5 경계를 넘는 것을 기다린
첫 StopReq 출력은 51.451초에서 51.014초로 약 0.437초 앞당겨졌다. 새 요청 시 기록된 속도는
약 1.265km/h, aEgo는 -0.497m/s²였다. 이후 차량 움직임은 기존 실패 기록 그대로이므로
후속 재시도 결과를 실제 개선/실패로 판정하지 않는다. 실차 정지 성능은 미검증이다.

2026-09-22 Ioniq 5 PE `00000f98--34cf514677--5`(5a970f1ad2)는 설정 ON과 조기 shouldStop을
확인했으나 첫 StopReq 이후 약한 감속이 남았다. 첫 송신 확인부터 서비스 브레이크 유지 신호까지
휠 속도 적분상 약 0.69m 이동했고 한 번의 재시도가 기록됐다. 이 거리는 정상 정지거리와의 차이가 아니다.
순정 bus2와 우리 출력의 InfoDisplay/byte7은 모두 0이지만 Lower는 0.04/0.20으로 달랐다.
ESC 감속 허용 요청은 재시도 전에 이미 복귀했으므로 재시도 효과나 내부 수락 조건을 단정할 수 없다.
당시 수렴 변경은 사용자 요청에 따라 첫 StopReq의 aReqValue -0.52→0 전환을 없애는 시험이었으며,
Lower와 재시도 조건은 유지한다. 기록 입력 재생과 단위 테스트는 실제 제동 효과를 검증하지 않는다.

현재 복원 이전의 양방향 수렴 구현으로 같은 기록의 carState/carControl 입력과 50Hz 송신 시각을 고정한 재생에서 첫 요구는 내부 값
-0.52→-0.504→-0.50, CAN 패킹 값 -0.52→-0.50→-0.50으로 이어졌다. 해제 54.886초와
재요청 55.887초는 같은 시점에 발생했다. 복구 및 재요청도 음수 출력을 이어갔으며 이 재생은
명령 변경에 따른 차량 움직임이나 새 가속도 계획을 예측하지 않는다.

2026-09-23 기존 방식 복원의 로컬 검증은 설정 경계·실시간 반영, 기존 플래너 정지 시점,
CAN 두 경로의 정상 정지/소프트홀드 가속도 동등성, 1회 재시도와 인터록을 포함한다.
이 복원이 실차 정지 충격이나 미정지 원인을 해결했는지는 아직 검증하지 않았다.
