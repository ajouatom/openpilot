# 신호 도우미 첫 주행 후 실패 분석 — 2026-10-11

사용자가 어젯밤 여러 신호에서 정지 후 출발하지 않았고, 오늘 아침에는 감지가
나빠졌다고 보고했다. 차량 로그와 영상을 수집해 확인했다. 녹색 전환 뒤 원본
모델의 출발 판단을 도우미가 막은 두 사례가 확인됐다. 정차 중 실행 확인과
기존 영상 재생만으로 실제 도우미의 주행 적합성을 확인하기에는 부족했다.
특히 실제 장면별 관측 간격과 추적 이력 소실을 놓친 것이 이번 실패에 관여했다.

이번 작업은 분석이다. 차량 코드, 모델, opt-in 설정을 변경하지 않았다.
신호 도우미는 조사 시점에도 ON이며, 이 보고서가 수정판 설치를 의미하지 않는다.

## 현재 모델과 수집 범위

- 차량은 `carrot-signal-shadow`의 `b80db2c97d`, tracked 파일 변경 없음.
- 주행 ONNX SHA-256은 기존과 동일한
  `f73a9e535523d5e9acb9e642c64e33d631825dc8ba74123757d107cedd047bb5`.
- 현재 `UsbGpuActive=0`, Jetlink의 `active=false`, `ready=false`를 확인했다.
  modeld의 `JoiningModel`은 외부 모델 연결을 감시하는 래퍼 이름이며,
  현재는 기존 내부 모델을 실행한다. 내부 컴파일 모델은 chunk 파일로 남아 있다.
- 추가한 것은 영상 관측·추적과 플래너의 적색 보강/정지 유지다. 별도로 사용자가
  요청한 b80의 CAN-FD 저속 StopReq/aReq 변경도 함께 설치돼 있다.
  기존 별도 모델 비교 기록도 켜져 있으나 그 출력은 주행 x·v로 채택하지 않는다.
- 설치 중 주차를 포함한 최근 46개 완료 구간의 qlog와 qcamera를 확보했다.
  실제 Drive가 포함된 야간 11개, 아침 12개 구간은 rlog와 두 전방 HEVC도 확보했다.
  수집 원본 161개, 총 2,210,770,889바이트가 차량 SHA-256과 모두 일치했다.
  조사 당시 기록 중이던 마지막 주차 구간은 수집 대상에서 제외했다.

69/13개를 물리적인 출발 지연의 정확한 반사실 추정값으로 해석하면 안 된다.

## 원인 1: 실제 관측 주기와 녹색 확인 조건이 맞지 않음

`SignalTracker.update`는 같은 track의 관측 간격이 125ms를 넘으면
`pending_since`를 다시 설정한다. 녹색에는 150ms 이상 이어지는 증거와 3개 이상
관측이 필요하다. 실제 처리가 150~200ms마다 한 번씩 들어오면, 매번 녹색을
검출하더라도 확인 시작점을 계속 뒤로 밀어서 green에 도달하지 못한다.

| 측정 | 야간 | 아침 |
|---|---:|---:|
| 관측 결과 수 | 5,191 | 5,444 |
| 125ms를 넘는 관측 간격 | 2,287 / 5,190 (44.1%) | 2,786 / 5,443 (51.2%) |
| 시간 범위 평균 관측률 | 7.91Hz | 7.58Hz |
| 관측기 계산 시간 p95 | 109.62ms | 114.54ms |
| 확정 green track을 포함한 결과 | 0 | 0 |
| 도우미의 green 해제 | 0 | 0 |

야간 구간 8의 track 1은 이전 적색 이력(`seen_red=true`)이 남아 있고,
55.753초 이후 같은 상자의 raw green이 반복되었다. 그러나 관측 간격이 대체로
150~200ms여서 state가 계속 unknown이었다.

해당 track의 실제 관측 103개를 격리해 같은 `SignalTracker.update`로 진단했다.
기록된 시각을 넣으면 확정 green은 0개, 관측 내용·상자·순서를 유지하고 간격만
100ms로 바꾸면 24개가 green이 된다. 간격 조건이 확인을 막는 것을 재현한 실험이며,
시각을 바꾸는 방식은 배포할 수정안도, 차량 처리 성능 개선도 아니다.

생산 직후 fresh인 관측은 야간 5,176/5,191개, 아침 5,374/5,444개였다.
생산 시 fresh라는 사실과 다음 플래너 호출에서 200ms 이내라는 것은 다르다.
새 결과 사이에서 예전 결과가 만료되는 경우도 있어서 플래너의 stale 기록이 나온다.
관측 fresh 비율만으로 녹색 확인이 가능하다고 평가한 것은 불충분했다.

## 원인 2: 한 번의 지연으로 적색 이력을 잃고 정지는 남음

야간 구간 6 첫 관측은 나이 208.0ms로 stale이었다. 현재 관측기는 이때
tracker와 session을 새로 만든다. 이후 실제 적색이 0.247/0.443/0.643/0.843초에
관측됐지만 약 200ms 간격이라 새 tracker는 적색 이력도 확정하지 못했다.
1.043초부터 같은 위치를 raw green으로 보아도 `seen_red=false`여서 green으로
인정할 수 없었다. 도우미의 정지 유지 상태는 그동안 계속 남았다.

즉 실패가 두 층에 걸친다. 관측 간격 조건이 확인을 막고, stale 결과 하나가
동일 신호의 이력까지 없앤다. 이후 도우미가 허용하는 해제 경로에 도달하지
못하면서 `hold_through_unknown`이 계속된다. 선택된 신호를 잃었는데도 정지
유지를 무기한 지속하는 구조가 이 두 실패와 결합했다.

## 아침의 미검출

아침 1094 구간 3의 적색 대기 장면에서 영상으로 신호등이 보이지만,
실시간 후보 목록은 해당 신호를 잡지 못했다. 구간 3 전체에서 확정 red track을
포함한 관측은 0개였다. 실제 빨간 신호가 보이는 한 HEVC 프레임을 현재 검출기에
넣어도 올바른 신호 후보는 없었고, 다른 영역의 raw green 후보만 나왔다.
이 후보는 green 확정/출발에 쓰이지 않았다.

현재 검출기는 학습된 범용 신호등 객체 검출기가 아니다. 어두운 가로 박스의
크기·비율·대비·좌우 색 위치 규칙에 의존하고, 야간 포화등 보강은 밝은 장면에서
꺼진다. 주간 장면에서는 이 후보 생성부터 실패하는 사례가 있다. 따라서
확인 시간만 바꾸어서는 아침 미검출을 고칠 수 없다. 이 표본에서 정확히 어떤
후보 조건이 최종 원인인지는 추가로 분해해야 하며 특정 조건 하나로 단정하지 않는다.

야간 13,126개와 아침 14,254개의 modelV2는 모두 valid였고, 모델 계산 시간
p95는 각각 27.90ms/30.90ms였다. 관측된 model frameDropPerc의 p99는 둘 다 0이다.
이는 모델 교체나 지속적인 계산 실패를 뒷받침하지 않는다. 그러나 같은 길을
같은 조건으로 도우미 ON/OFF 주행한 자료는 아니므로, 아침의 모든 체감 악화를
도우미 하나로 단정하거나 기존 모델의 신호 판단 자체가 항상 정상이었다고
말할 수는 없다.

## 다음 수정의 우선순위

1. 실제 관측 지연과 CPU 사용량을 포함해 시간 기반 확인 조건을 다시 설계한다.
   신선도 만료, 동일 객체 추적 이력, 연속 색상 증거를 각각 구분한다.
2. 지연·짧은 누락 후에도 같은 신호등임을 확인해 추적을 복구할 수 있게 한다.
   다른 신호의 녹색이나 단순 경과 시간으로 출발시키는 우회는 검증 대상이 아니다.
3. 주간의 실제 신호 상자가 후보에 올라오는지부터 개선·평가한다.
4. 이번 두 녹색 출발 실패를 필수 회귀 사례로 추가하고, 이전 적색 오출발 사례도
   함께 검사한다. 녹색 해제만 늘려 적색 오출발이 되살아나면 통과가 아니다.
5. 실제 장면에서의 관측 주기와 전송 지연을 재생에 반영하고, 정차 검증 후
   제한된 주행 검증을 별도로 수행한다.

현재 자료로 수정 우선순위는 정할 수 있다. 먼저 도우미 결함을 고치는 작업이
필요하며, 추가 데이터 수집이나 ONNX 재학습이 이 실패를 해결하는 선행조건은 아니다.
수정 전에는 도우미 OFF로 기존 경로를 사용하는 것을 권고한다. 본 분석에서는
사용자 차량의 ON 설정을 임의로 변경하지 않았다.

원본·프레임 검토·시각 재생·무결성 증거는 비공개
`.analysis/archive/2026-10-11-signal-followup/`에 보관한다. 차량 영상과 원시 로그는
커밋하지 않는다. `report/index.html`, `native_summary.json`, `probes.json`,
`collection_verified.json`이 주요 재현 결과다.
